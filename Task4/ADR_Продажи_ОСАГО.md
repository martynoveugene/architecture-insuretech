## front-to-back интеграция.

Сначала рассмотрим функциональное требование:
"Бизнесу важно, чтобы на экране пользователя предложения 
от каждой страховой компании отображались сразу, как только от неё пришёл ответ."

Для этого необходимо инкрементно доставлять результаты от каждой страховой как только они появились в системе.
Поэтому обычный REST запрос не подходит, он присылает данные целиком. 

Еще есть нефункциональное требование 
"Бизнес предполагает, что в пик нагрузки количество одновременных пользователей, создающих заявку на ОСАГО, 
может достигать 2,5 тысячи человек."

Это создаст большой RPS если реализовать short polling и опрашивать результаты короткими REST-запросами. 
Long polling REST-запрос подразумевает
синхронность и потребует большой пул потоков ОС, которые заснут на время, но будут потреблять память и будут заставлять
процессор переключать контекст.
Таким образом, для 2,5 тысяч человек одновременно необходим асинхронный подход с подключением WebSockets либо SSE.

В то же время активное он-лайн взаимодействие и полноценная двусторонность здесь не требуется, количество данных для клиента относительно невелико
и предсказуемо, но важно его доставлять по частям как только получен ответ от страховой.

В таком случае эффективным решением будет использовать SSE (Server sent events).
Рассмотрим ограничения SSE и убедимся, что они нам не мешают: 
- "только кодировка UTF-8" - в данном случае некритично - бинарные данные не предполагаются. 
- "один клиентский браузер может открыть только шесть одновременных подключений SSE" - укладывается в наш use case,
поскольку пользователь вряд ли будет запускать шесть расчетов одновременно.

Вместе с тем мы получаем плюсы SSE:
- Меньше накладных расходов на бэкенде.
- Работа поверх http - нет проблемы с фаерволами, есть проксирование и балансировка.
- Автоматическое переподключение. 

## back-to-back интеграция.

Из того же требования "Бизнесу важно, чтобы на экране пользователя предложения
от каждой страховой компании отображались сразу, как только от неё пришёл ответ."
следует, чтобы обработка на бекенде была асинхронной.
Например, реализуем через очередь задач с публикацией сообщения с запросом на опрос всех страховых.
Используется механизм точка-точка для обработчиков сообщений. То есть сообщение подхватывает обработчик osago-aggregator,
он делает в обработчике распараллеливание запросов к конкретным страховым.
Этот сервис хранит конфигурацию по страховым и знает с кем настроена интеграция. Таким образом, ответ на вопрос 
"Требуется ли ему своё хранилище данных?" - да, требуется. Это позволит выделить отдельный домен на ОСАГО-взаимодействия.
Для каждой задачи выставляется таймаут 60 секунд. Плюс внутри для вызова АПИ страховой выставляется меньший таймаут.
Далее, нужно кроме подачи заявки еще успеть получить результат. И мы не знаем через какое время он будет доступен,
поэтому делаем несколько попыток (Retry).

На следующих этапах возможно усовершенствовать эту модель путем добавления асинхронности для опроса конкретной страховой.
То есть osago-aggregator берет один запрос от клиента на расчет и порождает несколько задач в доступные страховые компании.
Поскольку в первом варианте сообщение будет считаться обработанным после получения ответа от самой медленной страховой.

В обоих случаях после получения ответа от страховой osago-aggregator создает ответное сообщение с результатами
для core-app, а обработчик на стороне core-app отправляет этот результат в SSE сессию. Для нее также установлен таймаут.

Такой подход даст возможность автоскейлинга для обработчиков - количество обработчиков можно увеличивать без проблем.

Поскольку по условиям "core-app — монолитное бэкенд-приложение", то ответные осаго-сообщения будут обрабатываться в единственном
его инстансе, то есть там же где ждут sse-сессии. А если и когда этот core-app будет иметь много инстансов, то нужно будет
решить проблему доставки осаго-ответа тому экземпляру, где ждет соответствующая sse-сессия от клиента.


## Альтернативы.
Поскольку в следующем задании рассматривается вариант перехода на GraphQL в сервисе client-info, 
и команда освоит GraphQL так или иначе,
то можно рассмотреть применение здесь GraphQL Subscriptions. Но SSE видится быстрее реализуемым в данном случае.

## Применение паттернов отказоустойчивости.

Поскольку core-app - монолитный сервис и самый нагруженный, то он требует особого внимания с точки зрения отказоустойчивости.
Позаботимся о нем в первую очередь и окружим паттернами:
- Rate limiter на входе core-app нового метода расчета ОСАГО - относительно rps всех клиентов.
- Timeout - на это же взаимодействие по расчету ОСАГО между web и core-app.
- Rate limiter на оформление страховок партнерами в core-app - лимит по каждому партнеру отдельно.
- Timeout на внешнее взаимодействие core-app по оплате страховок
- Circuit Breaker для синхронного взаимодействия core-app с client-info, поскольку оно синхронно и лучше избавиться от влияния проблем client-info
- Существует еще одно синхронное взаимодействие из ins-comp-settlement в core-app, но оно работает ночью и в не самом критичном сервисе, т.о. не обязательно для охраны. 
- Transactional outbox - для надежной записи запросов по ОСАГО из core-app в очередь.

Далее, для остальных сервисов:
- Circuit Breaker выглядит необходимым для синхронных вызовов из osago-aggregator в Системы страховых компаний, поскольку здесь очень жесткое требование
уложиться в 60 сек для всего end-2-end бизнесс-процесса получения предложения ОСАГО, так что недоступность одного внешнего АПИ может усложнить весь процесс.
Circuit Breaker должен работать независимо для каждого внешнего АПИ.
- Timeout-ы на внешние онлайн вызовы в Системы страховых компаний.
- Retry на вызов из osago-aggregator в Системы страховых компаний, по бизнес flow.
