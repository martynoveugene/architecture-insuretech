# Задание 1. Проектирование технологической архитектуры

Сделаем архитектурную трансформацию для решения проблем компании.
Каждая из трех проблем послужит отправной точкой для решения.
Сразу скажем, что вертикальное масштабирование это тупиковый путь для компании планирующей глобальное присутствие.
 
## 1. Сайт медленно загружает страницы.
Проблема: "максимально зафиксированная нагрузка на запросы поиска составила 50 RPS, а на запросы оформления — 10 RPS."
Видим, что запросов на чтение в 5 раз больше, чем запросов на запись, то есть преобладает читающая нагрузка.
В этом случае хорошо работает cqrs-паттерн. То есть создаем slave реплику базы core-db и перенаправляем 
чтения на эту реплику. Далее, существует требования "сервис должен обслуживать клиентов из всех часовых поясов"
и "сделать упор на развитие в регионах РФ" поэтому будем стараться расположить данные поближе к клиенту. 
Сделаем несколько кластеров в разных зонах доступности. Поскольку каждый клиент имеет географическую привязку и
работает в основном только со своими данными, то подавляющее число взаимодействий может быть перенаправлено к ближайшему
кластеру. Поэтому кластеры будут независимыми в каждой зоне.  

Для базы выберем PostgeSQL Patroni - шаблон конфигурации, который позволяет добиться высокой доступности и отказоустойчивости распределённого кластера PostgreSQL.

Это обеспечит паттерн Bulkheading - при недоступности кластера одной зоны, остальные зоны продолжат работу.

## 2. Нарушается SLA для B2B-клиентов. 
Причина уже известна "один из партнёров «сжирал» все ресурсы приложения" и это служит источником решения.
Применим паттерн "Rate Limiting" для входящих запросов по API. Ограничим скорость входящих запросов к API
в соответствии с договоренностью - 20 RPS для каждого партнера. Необходимо взять продвинутый gateway
от которого требуется две вещи - способность декодировать jwt-токен, чтобы определить идентификатор клиента.
И способность ограничивать входящие запросы.
Например, подходит Apache APISIX. Есть плагин jwt-auth для декодирования токена и есть плагин limit-req для 
настройки лимита. 
Если использование продвинутого gateway не предполагается, то "Rate Limiting" будет работать относительно 
ip-адреса источника запроса. 

## 3. Приложение падает. Команда реагировала на проблему очень медленно. 
Здесь требуется уменьшить время "MTTR, mean time to recovery", оно складывается из двух промежутков
"MTTD, mean time to detect" и "Repair time". Про второй необходима дополнительная информация и анализ как его можно уменьшить.
Но тут явная проблема с первым этапом обнаружения падения, поскольку команда "узнавала о ней от пользователей" и первым
этапом нужно уменьшить именно это время. Необходимо настроить систему алертинга.

### Уведомления.
В кубернетес для этого служит связка Prometheus + Alertmanager + Grafana.
Prometheus непрерывно собирает метрики с кластера. В нем же настроены правила PromQL Rules вида "если CPU > 85% дольше 5 минут",
которые порождают алерт и отправляют его в Alertmanager. Alertmanager анализирует и группирует похожие алерты и решает куда
отправить уведомление. Отправляет уведомление в настроенный канал.

### 4 уровня проверок.
- Уровень инфраструктуры, железа на котором работает кластер. 
Проверяется нехватка свободного места на дисках, высокая утилизация RAM/CPU, сетевые ошибки на интерфейсах.
- Уровень компонентов Kubernetes.
Проверяются конкретные поды. Правила вида - постоянный перезапуск пода, под не может перейти в состояние готов, проблемы с сертификатами.
- Уровень приложений. Для этого нужна уже доставка кастомных метрик в Prometheus. Отслеживается количество ошибочных http ответов, 
увеличение времени ответа Latency, состояние очередей.
- Уровень логов и аудита. Алертинг по текстовым логам. Поиск строк вида FATAL, OOM Killed или Segfault в логах контейнеров.

Быстрый алерт даст больше времени на восстановление. Основное время из RTO = 45 минут (Recovery Time Objective) будет потрачено на решение проблемы.

Для обеспечения RPO = 15 минут (Recovery Point Objective), необходимо настроить инкрементные бекапы баз раз в 15 минут
и один полный бекап - раз в сутки.

Для общих данных "информацию о продуктах и тарифах" - репликация должна обеспечивать актуальность данных не более 15 минут.

## Фейловер-стратегия.

В требованиях есть "доступность приложения должна быть равна 99,9%" и "RTO — 45 мин".
Исходя из этого Active-Standby стратегия не подходит, поскольку она обеспечивает только доступность =< 99,5%.
Таким образом необходимо использовать стратегию Active-Active.

Она заключается в том, что есть несколько узлов обрабатывающих трафик. 
При этом перед ними стоит балансировщик, который этот трафик распределяет между узлами. 

Еще есть требования "сервис должен обслуживать клиентов из всех часовых поясов" и "сделать упор на развитие в регионах РФ".

Таким образов, эти несколько узлов должны быть распределены географически.
